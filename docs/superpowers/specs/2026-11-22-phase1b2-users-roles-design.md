# Phase 1-B2 설계 — 재인증·사용자·역할

작성 2026-11-22. 사용자에게 위임받은 역할 에이전트(제품·보안)가 정한 결정(`docs/decisions.md` 「Phase 1-B 결정」 Q2·Q7~Q11·Q14·Q16)을 옮겼다 — **사용자 확인 전**이다. 결정이 없던 두 질문(16절 Q18·Q19)은 같은 역할 에이전트가 정해 채웠다(2026-11-22).
근거: 1-A 스펙 `2026-11-14-phase1a-auth-design.md`, 1-B1 스펙 `2026-11-21-phase1b1-admin-shell-design.md`, ondolith 원문 D10(FR-704·723·725·726)·D13(A-401~405)·D15(5.1 R1~R9, 5.2, 5.3-1, 5.4, 7절)·D19(A-401~405)·D86, 원문 코드(문서가 침묵하는 곳만: A-401 검색·쪽, 처리기 검사 순서).

## 2. 데이터 (V4 마이그레이션, 앞으로만)

- 표는 더하지 않는다. `users`·`roles`·`user_roles`·`role_permissions` 는 V1·V2 그대로다.
- 권한 씨앗(D15 2.2·2.5 의 키 중 1-B2 가 쓰는 것만, V2 「쓰는 권한만 심는다」). enum `Permission` 에 같은 커밋으로 더한다 — 아니면 기동 점검 2번이 멈춘다.

  | 키 | 설명 | 쓰는 곳 | 시드 |
  |---|---|---|---|
  | `user.view` | 사용자 목록을 본다 | A-401 | `operator` |
  | `user.create` | 사용자를 만든다 | A-402 생성 | — |
  | `user.update` | 사용자 상세를 보고 활성 상태를 바꾼다 | A-402 상세·비활성·활성 | — |
  | `role.view` | 역할과 권한 구성을 본다 | A-403 | `operator` |
  | `role.assign` | 사용자에게 역할을 주고 뺀다 | A-405 | — |
  | `role.manage` | 역할에 권한을 주고 뺀다 | A-404 | — |

  `editor` 에는 주지 않는다. `admin` 은 `is_superuser` 라 행이 없다. 「—」는 `admin` 만 갖는다는 뜻이고 방어가 아니다(D15 5.1 끝) — 설치처가 A-404 로 다른 역할에 줄 수 있다.
- **M-5(V3 주석)**: V3 의 「WHEN 이 그 하나만 통과시킨다」는 사실보다 넓다 — 사용자가 남아 있어도 `UPDATE … SET actor_user_id = NULL` 만 하는 문장은 통과한다(원문과 같은 한계, `actor_email` 스냅샷은 못 바꾼다). **V3 파일은 고치지 않는다** — 이미 적용된 설치처에서 체크섬이 달라지면 Flyway 검증이 기동을 멈출 수 있다(주석도 체크섬에 드는지는 구현 때 확인, 확인 전에는 손대지 않는다). V4 머리 주석과 시험 이름으로 바로잡는다. 트리거는 강화하지 않는다: 앱 코드에 `UPDATE operation_logs` 가 없고, 트리거는 우리 코드의 사고를 막는 장치다(1-B1 2절). 화면에 「(삭제된 계정)」으로 잘못 보이는 한계는 14절에 적는다.

## 3. 재인증 (Q2·Q16)

### 3.1 창

- 세션 속성 셋: `ondolithj.user_id`·`ondolithj.auth_at`(필수, 1-A 그대로), `ondolithj.reauth_at`(`Instant`, **선택**).
- 로그인 성공과 재인증 성공 때 앱 시계로 `reauth_at` 을 찍는다. 로그인은 세션 저장(`saveContext`) 바로 뒤에 찍는다.
- 열림 판정 `open(값, 지금)`: 값이 `Instant t` 이고 `t ≤ 지금 < t + 15분` 이면 열림. 값이 없음·다른 타입·미래(시계가 뒤로 감)면 닫힘이다. **닫힘은 세션을 버리지 않는다** — 1-A 의 「속성이 없거나 타입이 다르면 세션을 버린다」는 필수 둘에만 걸린다(지금 `SessionContextRepository` 도 그 둘만 본다). 1-B2 이전에 로그인한 세션은 jar 교체 뒤에도 로그인이 유지되고 창만 닫혀 있다.
- 거는 곳: 처리기 첫 줄 `reauth.require(request)` 하나. 닫혀 있으면 `ReauthRequired` 를 던지고 `ApiErrors` 가 403 Problem Details 로 바꾼다. Q16 의 `require(session)` 대신 요청을 받는다 — MVC 가 넣는 `HttpSession` 인자는 세션이 없으면 만든다. 속성 이름과 판정은 `auth/Reauth.java` 한 파일에 둔다.
- 대상(D15 5.3-1 의 1-B2 행, 원문과 같다): A-402 비활성·활성, A-404 부여·빼기, A-405 부여·빼기. 여섯이다. A-402 생성, A-201 저장, 재인증 자체는 대상이 아니다.
- **순서: 재인증은 처리기 본문의 첫 줄이다**(권한 표시와 MVC 인자 해석 뒤, 본문의 입력 검사·대상 조회·R 규칙 앞). 원문 코드도 그렇다(`guardAccountOp`·`RoleAssign`). 인자 해석에서 나는 경로 UUID 404 와 읽을 수 없는 본문 400 은 재인증 403 보다 먼저 나올 수 있다(구현 때 확인) — 둘 다 아무것도 바꾸지 않고 기록하지 않는다. 그래서 재인증 대상 여섯은 `@Valid` 애너테이션 검증을 쓰지 않고 칸 검사를 본문에서 한다(6절의 「재인증 → 422」 순서). 창이 닫힌 요청은 아무것도 바꾸지 않고 **작업 로그에도 남지 않는다** — R 위반 행은 창이 열린 요청(로그인 또는 재인증 뒤 15분 안)만 만든다(지울 수 없는 표를 키우는 길을 줄인다, Q13 과 같은 논리).

### 3.2 재인증 전용 403

```json
{"type": "urn:ondolithj:problem:reauth-required", "title": "Forbidden", "status": 403, "detail": "비밀번호를 다시 입력하세요"}
```

- `type` 은 이 하나다. 설치처 도메인을 담지 않는 URN 이다(배포형이라 절대 URL 을 박지 않는다). 다른 403(권한 없음·CSRF·R 위반)은 지금처럼 `about:blank` 다. 프런트는 `type` 만 보고 가른다.
- 401 을 쓰지 않는다(1-A 프런트는 401 을 「로그인이 끝났다」로 읽는다). 리다이렉트하지 않는다. 창 상태는 어디에도 내주지 않는다(Q16).

### 3.3 `POST /api/admin/reauth`

- 표시 `@RequiresPermission(ADMIN_ACCESS)`(관리자 경로에서 허용되는 표시, Q1). CSRF·관리자 IP 60회/분을 그대로 받는다. 파일 `auth/ReauthController.java`.
- 본문 `{"password": "..."}`. 고정 레코드, 1~1000자(로그인과 같은 상한) — 넘거나 없으면 422 `errors.password`. `toString` 은 비밀번호를 가린다(Phase 0 `InstallRequest` 와 같다).
- 순서: ① 횟수 제한 `reauth:<user_id>` 5회/분(`ondolithj.rate-limit.reauth`, 기본 5, 1-A 고정 창 제한기). 넘으면 429 + `Retry-After` — 대조 전에 거른다. ② 요청자의 이메일로 대조. ③ 성공 → `reauth_at` 을 찍고 204. 세션 ID 는 바꾸지 않는다(인증 주체가 같다, Q16). ④ 틀림·72바이트 초과 → 3.2 의 403.
- 앱 로그: 성공·실패 INFO 「재인증 성공·실패: 사용자 <id>」. 이메일·비밀번호는 남기지 않는다. 작업 로그에는 남기지 않는다(원문과 같다).

### 3.4 처리기 대조 시험

- `ReauthTargetsTest` 는 운영 컨텍스트의 `RequestMappingHandlerMapping` 에서 `/api/admin/**` 의 GET 이 아닌 처리기를 모두 읽는다(지금은 모두 POST — 나중의 DELETE 등도 분류를 빠져나가지 못하게). 시험 안의 표 둘(재인증 대상 여섯 / 대상 아님 셋: `settings`·`users`(생성)·`reauth`)과 대조한다.
- 어느 표에도 없는 처리기가 있으면 실패한다 — 새 상태 변경 API 는 분류를 강제받는다(D15 5.3-1 「처리기↔표를 시험이 대조한다」).
- 대상 표의 처리기는 창이 닫힌 세션으로 부르면 3.2 의 403 이고, DB 가 그대로다. 대상 아님 표의 처리기는 그 `type` 을 내지 않는다.

## 4. 사용자 (A-401·A-402)

- 파일 `admin/UsersController.java`. 1-B1 관례대로 권한 표시는 메서드마다 단다.
- **A-401** `GET /api/admin/users?page=1&q=` — 원문 코드 값(문서에 없음): 쪽당 50, 한 행 더 읽어 `has_next`, 전체 건수는 세지 않는다. `q` 는 앞뒤 공백을 뺀 뒤 이메일·표시 이름의 **일부**를 `ILIKE` 로 찾고, `%`·`_`·`\` 는 글자 그대로 찾게 이스케이프한다(원문 `SearchUsers`). 정렬은 `created_at DESC, id`. 역할 키는 같은 질의의 `array_agg` 로 — 질의는 행 수와 관계없이 하나다(D86 7.3). 비밀번호 해시·기준 시각은 싣지 않는다(D13). `page` 는 A-601 과 같다(1 미만 422 `errors.page`, 정수가 아니면 400, offset 은 long). `q` 는 200자를 넘으면 422 `errors.q`(쪽 상한처럼 입력 상한을 둔다, D15 SC-4).
- **A-402 상세** `GET /api/admin/users/{id}`: `user.update`(D19 — 목록의 `user.view` 와 다르다. 운영자는 목록만 본다). 사용자 칸과 가진 역할, A-405 부여 칸에 쓸 「줄 수 있는 역할」 목록(`is_assignable`)을 함께 낸다. 질의 셋(사용자·가진 역할·줄 수 있는 역할), 행 수와 무관.
- **생성** `POST /api/admin/users`: `user.create`. 재인증 대상이 아니다.
  - 본문 `{email, display_name, password}` — 고정 레코드. 역할·활성 상태·기준 시각은 받지 않는다(D19).
  - 이메일: 설치와 같은 검사(형식·254자), 앞뒤 공백을 빼고 소문자로 저장. 중복은 DB `UNIQUE` 가 막고 409 「이미 사용 중인 이메일입니다」(먼저 세지 않는다 — 동시 생성 둘이 다 지나간다).
  - 표시 이름: 1~50자(Q9). 사이트 이름과 같은 규칙 — 앞뒤 공백(NBSP 포함)을 빼고, 공백·보이지 않는 문자만이면 「필수입니다」, 제어 문자가 있으면 「쓸 수 없는 문자가 있습니다」(1-B1 의 U+0000 → 500 교훈). 같은 함수에 상한만 인자로 준다(서버 `SiteName`, 프런트 `siteName.ts`).
  - 비밀번호: 설치와 같은 두 검사 — 10자 이상, UTF-8 72바이트 이하. 두 검사를 한 함수로 모아 설치와 함께 쓴다. 확인 칸은 프런트에만 있다(9절) — 원문 A-402 입력표에 확인 칸이 없고, 서버 레코드에 칸을 늘리지 않는다.
  - 저장: `email_verified_at = now()`(관리자가 보증한 주소, D19), 역할 없음. 201 `{"id": "<uuid>"}`.
- **비활성** `POST /api/admin/users/{id}/deactivate`·**활성** `…/activate`: `user.update`. 본문 없음.
  - 순서: 재인증(3.1) → 대상 없음 404(남기지 않음) → 자기 계정 403 「자기 계정에는 이 작업을 할 수 없습니다」(남김) → R6 → (비활성만) 마지막 관리자(5절) → 쓰기 → 기록.
  - R6: 대상이 superuser 역할 보유자(활성 여부 무관)인데 요청자가 superuser 가 아니면 403(남김). **비활성과 활성 둘 다에 건다**(Q19). 활성화는 막아 둔 계정을 다시 여는 일이다(D19 재인증 행, 원문 코드). 1-E 전에는 비활성화가 유일한 탈취 대응이라(Q11), 비-superuser 가 superuser 보유자를 다시 열면 막은 효과가 사라진다. D15·D19 의 R6 목록(비활성·삭제·재설정)보다 넓다(ondolith-j 결정).
  - 비활성 쓰기: `UPDATE users SET is_active = false, sessions_valid_from = GREATEST(now(), sessions_valid_from + interval '1 microsecond'), updated_at = now() WHERE id = ?`. 그 계정의 모든 세션이 다음 요청에서 거부되고, 재활성화가 옛 세션을 살리지 않는다(Q11, D86 1.19).
  - 활성 쓰기: `is_active = true` 만. 기준 시각은 건드리지 않는다(이미 비활성화 때 옮겼다). 잠금이 필요 없다(늘리는 방향, Q10).
  - 이미 그 상태여도 204 이고 기록한다(원문 코드와 같다 — 성공 응답마다 남긴다).
  - 자기 계정·대상 비교는 `UUID` 값끼리(D86 2.10). 대문자 경로도 같은 사람이다.
- 요청자의 superuser 여부는 `Actor` 에 칸 `superuser` 를 더해 싣는다. `ActorQuery` 가 이미 같은 질의에서 계산한다(R9 대로 `anonymous`·`member` 의 표시는 세지 않는다). 「권한 전부를 가졌다」로 대신하지 않는다 — A-404 로 모든 권한을 받은 역할이 superuser 가 되면 안 된다.

## 5. 마지막 관리자 잠금 (Q10, D15 5.2)

- 파일 `admin/LastAdmin.java`, 함수 하나. A-402 비활성과 A-405 의 superuser 역할 빼기가 부른다(나중의 삭제도 이것을 쓴다).
- 한 트랜잭션(`TransactionTemplate`) 안에서:
  ```sql
  SELECT id FROM roles WHERE is_superuser FOR UPDATE;           -- 직렬화
  SELECT count(*) FROM users u JOIN user_roles ur ON ur.user_id = u.id
    JOIN roles r ON r.id = ur.role_id AND r.is_superuser WHERE u.is_active;
  ```
  **거절 조건: 대상이 활성이고 superuser 역할 보유자이며, 활성 보유자 수 ≤ 1.** 거절이면 롤백하고 409. 아니면 같은 트랜잭션에서 쓰고 커밋한다.
- 식으로 답이 나오는 경우: 비활성 보유자의 역할 빼기는 통과(셈에 들지 않는다). 이미 비활성인 계정의 비활성화는 통과(대상이 활성이 아니다). 보유자가 아닌 계정은 늘 통과.
- **기록은 트랜잭션 밖에서 한다** — 성공 행은 커밋 뒤, 409 거절 행(남김, D19)은 롤백 뒤. 기록 실패가 일을 되돌리지 않는다(1-B1 4.1).
- **순차 API 로는 409 에 닿지 않는다.** 대상이 superuser 보유자면 R6·R3 때문에 요청자도 superuser 여야 하고, 요청자는 활성이라(로그인했다) 셈에 들며, 자기 계정 금지·R1 때문에 대상과 다르다 — 셈이 2 이상이다. 409 는 두 관리자가 서로를 동시에 조작할 때만 나온다. 그래서 시험은 함수를 직접 부르는 시험과 동시 요청 시험이다(12절).
- 앞선 요청이 커밋한 뒤 잠금을 얻은 요청은 새 문장 스냅샷으로 센다(READ COMMITTED). 요청자 자신이 방금 비활성화됐어도 그 요청은 시작 때 인증을 지났다 — 불변식(활성 관리자 ≥ 1)은 잠금이 지킨다(15절 3).

## 6. 역할 (A-403·A-404·A-405)

- 파일 `admin/RolesController.java`. R2·R4 는 이 파일의 **판정 함수 하나** `covers(actor, 권한 집합)` — 요청자 유효 권한이 그 집합을 모두 갖는가. superuser 역할의 권한 집합은 「코드의 권한 전부」로 본다(`role_permissions` 행이 0 이라 빈 집합으로 통과하면 안 된다). R3 은 R2 와 독립으로 먼저 본다.
- **A-403** `GET /api/admin/roles`: `role.view`(Q8).
  - 응답 `{"roles": [{id, key, name, description, is_builtin, is_superuser, is_assignable, permissions: [{key, effective}]}], "permissions": [{key, description}]}`. 뒤의 `permissions` 는 A-404 가 고를 목록이다.
  - `effective` 는 서버가 정한다: `anonymous`·`member` 의 방문자 권한 밖 부여는 `false`(D15 R9, 1-A 불러오기와 같은 규칙). 화면은 「효력 없음 — 빼세요」로 보인다(FR-723).
  - superuser 역할은 `permissions` 가 비고 화면이 「모든 권한(편집할 수 없음)」으로 보인다.
  - 질의 둘(역할+부여 집계, 권한 목록), 행 수와 무관. 정렬은 `key`.
- **A-404 부여** `POST /api/admin/roles/{id}/permissions` `{"permission": "user.view"}`, **빼기** `…/permissions/revoke` 같은 본문: `role.manage`.
  - 부여 순서: 재인증 → 역할 없음 404 → 모르는 키 422 `errors.permission` 「알 수 없는 권한입니다」(남김) → R5 superuser 역할 403 「이 역할의 권한은 변경할 수 없습니다」(남김) → R9 `anonymous`·`member` 에 방문자 권한 밖 422 `errors.permission` 「모두가 갖는 역할에는 방문자 권한만 줄 수 있습니다」(남김) → R4 403 「보유하지 않은 권한은 부여할 수 없습니다」(남김) → `INSERT … ON CONFLICT DO NOTHING` → 204, 기록.
  - 1-B 에는 방문자 권한이 없어 두 역할로의 부여는 모두 422 다. 자기가 속한 역할도 거부하지 않는다(R4 가 막는다, D19).
  - 빼기 순서: 재인증 → 404 → 모르는 키 422(남김) → R5(남김) → R4(남김) → 삭제, 0행이면 404 「그런 부여가 없습니다」 → 204, 기록. **R9 는 빼기에 걸지 않는다** — 잘못 들어간 것을 빼는 길이다(D13).
- **A-405 부여** `POST /api/admin/users/{id}/roles` `{"role_id": "<uuid>"}`, **빼기** `…/roles/revoke` 같은 본문: `role.assign`.
  - 부여 순서: 재인증 → 사용자·역할 없음 404 → `is_assignable = false` 422 `errors.role_id` 「줄 수 없는 역할입니다」(공통 규약 「읽었지만 받을 수 없음」, 남기지 않음) → R1 자기 계정 403 「자기 계정의 역할은 변경할 수 없습니다」(남김) → R3 superuser 역할인데 요청자가 superuser 아님 403 「이 역할은 관리자만 부여할 수 있습니다」(남김) → R2 403 「보유하지 않은 권한이 포함된 역할입니다」(남김) → `INSERT … ON CONFLICT DO NOTHING`(이미 있으면 그대로, 멱등) → 204, 기록.
  - 대상 계정이 비활성일 때: 거부하지 않는다. 역할과 활성 상태는 별개다(D19 거부 조건, Q18). superuser 역할은 대상이 비활성이어도 R3 대로 superuser 만 준다. 비활성 보유자는 마지막 관리자 셈에 들지 않으므로 부여·빼기 모두 잠금 판정을 바꾸지 않는다.
  - 빼기 순서: 부여와 같은 R1·R3·R2(D13) → 갖지 않았으면 404 「그 사용자는 이 역할을 갖고 있지 않습니다」 → superuser 역할이면 5절의 잠금 아래서 지운다(409 「마지막 관리자의 역할은 회수할 수 없습니다」, 남김) → 204, 기록.
  - 이메일로 대상을 찾는 입구(원문 A-403 의 폼)는 두지 않는다(Q18). 입구는 A-402 상세의 `user_id` 하나다. `role.assign` 은 있고 `user.update` 가 없는 역할은 부여 화면이 없다 — 화면이 열리지 않는 쪽으로 실패하고 API 는 그대로 된다. `ponytail:` 설치처가 그런 역할을 쓰면 A-403 에 이메일 입구(활성 회원만, 부여만)를 더한다. 원문의 「부여 현황 GET `role.assign`」도 그때 본다.
  - 세션 부수효과는 없다. 권한은 요청마다 DB 에서 읽으므로 다음 요청부터 반영된다(1-A).
- body 의 `role_id` 가 UUID 가 아니면 본문을 읽을 수 없는 것이라 400 이다(경로 변수만 404).

- **경로 UUID**: 형식이 틀리면 404 「찾을 수 없습니다」(D86 2.7). 비교는 `UUID` 값끼리라 대소문자 표기로 우회할 수 없다(D86 2.10). Spring 의 문자열→UUID 변환이 표준이 아닌 짧은 꼴(`0-0-0-0-1`)도 받는지는 구현 때 확인 — 받더라도 값으로 비교하므로 우회는 아니다.
- **M-7**: 기동 점검이 `/api/` **바로 다음 마디**에 `{`·`*` 가 든 매핑(`/api/{area}/x`·`/api/*/x`·`/api/**`)을 거부한다. 그런 매핑은 `/api/admin/x` 요청을 받지만 관리자 경로로 세지 않는다. 더 깊은 마디의 변수(`/api/admin/users/{id}`)는 그대로 된다.

- 이름은 V3 CHECK(`^[a-z][a-z0-9]*\.[a-z][a-z0-9_]*$`)를 통과한다. 규칙 토큰은 `self`·`r1`·`r2`·`r3`·`r4`·`r5`·`r6`·`r9`·`last_admin`·`unknown_permission` 뿐이다.
- **칸 출처(1-B1 4.3 그대로)**: `summary` 에는 코드 상수, enum 으로 검증된 권한 키, DB 에서 읽은 역할 키(V1 CHECK 형식)만 넣는다. **모르는 권한 키 거절 행에 그 키를 넣지 않는다** — 요청 본문 문자열이다. `target_id` 는 경로에서 읽은 UUID 를 `toString` 한 값이다.
- 남기지 않는 것: 권한 없음 403, 재인증 403, 404, 이메일 중복 409, `is_assignable` 422, 재인증 성공·실패(D19 오류표 그대로).
- **원문 코드와 다른 곳**: 원문 코드는 A-402 의 자기 계정·R6·마지막 관리자 거절을 기록하지 않고, 동작 이름을 `user.update`·`role.assign` 으로 뭉친다. 문서(D19 「남김」, D15 5.1 「위반 요청은 403이고 작업 로그에 남긴다」)를 따르고, A-601 에서 무엇이 있었는지 보이게 동작을 나눈다. 같은 값으로 다시 하는 성공(이미 비활성, 이미 부여)도 남기는 것은 원문 코드와 같다(D13 「전 작업이 작업 로그 대상」).

## 9. 프런트

- **화면 표**(`AdminLayout.tsx`): 메뉴 항목 `/admin/users` 「사용자」(`user.view`), `/admin/roles` 「역할」(`role.view`)을 더한다. 하위 주소 `/admin/users/new`(`user.create`)·`/admin/users/:id`(`user.update`)는 같은 표에 메뉴 없이 둔다. 관리자 쿼리 키는 모두 `["admin", …]` 아래다(1-B1 I-1). 표 주석에 이 규칙을 한 줄 적는다. **M-4**: `<Route index element={null} />`.
- **`useSave` 확장**(`shared/api/useSave.tsx`)
  - 403 은 `type` 으로 가른다. 재인증 `type` 이면 「재인증 필요」 상태가 되고 보낸 값을 메모리(ref)에 남긴다. 그 밖의 403·404·409 는 서버 `detail` 을 보이고(코드 상수 문구, React 가 이스케이프), 없으면 지금 문구를 쓴다.
  - `reauth(password)`: `POST /api/admin/reauth` 를 부른다. 204 면 남긴 값으로 원 요청을 **한 번** 다시 보낸다. 403 이면 칸 옆에 「비밀번호가 맞지 않습니다」, 429 는 「잠시 뒤 다시 시도하세요」, 401 은 로그인 안내다. 다시 보낸 요청이 또 재인증 403 이면 대화상자가 다시 묻는다(사용자가 누를 때만 보내므로 저절로 되풀이되지 않는다).
  - **비밀번호는 상태·쿼리 캐시에 두지 않는다.** 재인증 요청은 `useMutation` 을 거치지 않는다 — 변경의 `variables` 가 캐시에 남는다(추정, 구현 때 확인). 입력 칸은 제어하지 않는 칸이고, 대화상자가 닫히면 사라진다.
  - `cancel()`: 남긴 값과 재인증 상태를 버린다. 잠금은 응답이 올 때마다 이미 풀려 있다.
  - **M-1**: 선택 인자 `focus(field)` 에 폼의 `setFocus` 를 넘기면, 서버 422 의 첫 오류 칸으로 초점을 옮긴다(설치 화면과 같은 방식).
  - **M-2**: 422 는 칸 옆 메시지만이고 `role="alert"` 알림을 띄우지 않는다. 초점이 칸으로 가면 `aria-describedby` 가 읽어 준다. 1-B1 스펙 6절 「모두 `role="alert"`」는 422 를 빼고 읽는다 — 이 문장이 대신한다.
  - `onSuccess` 가 응답 본문을 받는다(생성의 `id`).
- **알림**(`notice.tsx`): 알림이 보일 주소를 함께 갖는다(기본은 지금 주소). 지금은 주소가 바뀌면 지워서, 생성 뒤 상세로 옮기면 알림이 사라진다. 생성은 상세 주소를 넘긴다. 그 주소를 떠나면 없다는 규칙은 같다.
- **확인 단추**(`shared/ui/confirm.tsx`, FR-725·726·727): 단추 하나가 동작 하나를 맡는다. 인자는 단추 글, 대화상자 제목·설명, `destructive` 여부, `useSave` 결과, 보낼 값이다.
  - `destructive` 면 누를 때 확인 대화상자가 뜨고, 「취소」는 요청을 보내지 않는다(잠그지 않는다). 대상: 비활성화, 역할 빼기, 권한 빼기(FR-725 의 1-B2 해당분).
  - `destructive` 가 아닌 재인증 대상(활성화, 역할 부여, 권한 부여)은 누르면 바로 보낸다. 재인증 403 이 오면 같은 대화상자가 비밀번호 칸만으로 뜬다.
  - 확인 대화상자가 열려 있을 때 재인증 403 이 오면 같은 대화상자에 「관리자 비밀번호 재확인」 칸이 더해진다. 칸은 서버가 물을 때만 나오고, 나오면 필수다(D15 5.3-1). 칸은 `type="password"`·`autocomplete="current-password"` 다.
  - 「처리 중…」과 두 번 누름 방지는 `useSave` 의 잠금을 그대로 쓴다. 성공하면 대화상자를 닫고 알림을 띄운다.
- **조회 화면 공용**: 401 이면 「로그인이 끝났습니다」와 `/login?next=` 링크를 `SaveAlert` 와 같은 모양으로 보인다(M-9 앞부분). 403 이면 「권한이 없습니다」, 그 밖은 `role="alert"` 「…를 불러오지 못했습니다」다. `can` 을 읽는 화면은 `/api/me` 실패를 「권한이 없습니다」가 아니라 「불러오지 못했습니다」로 보인다(**M-10**, 사이트 설정 포함).
- **쪽 나누기**(작업 로그·사용자 목록): 쪽이 바뀌면 h2 로 초점을 옮긴다(**M-3**, `useFocusOnMount` 가 의존 값을 받는다). 주소의 `?page=` 가 양의 정수가 아니거나 2147483647 을 넘으면 1쪽으로 본다. 빈 쪽인데 `page > 1` 이면 「이전」 대신 「첫 쪽으로」를 보인다(**M-9** 뒷부분 — 범위 밖 주소를 손으로 고쳤을 때).
- **사용자 목록**: 표(이메일·표시 이름·상태·역할·만든 날). 이메일은 `can['user.update']` 일 때만 상세 링크다. 검색 칸 하나(GET 폼이라 잠그지 않는다, 주소의 `?q=`). `can['user.create']` 면 「새 사용자」 링크.
- **새 사용자**: 이메일·표시 이름·비밀번호·비밀번호 확인. zod 는 서버와 같은 규칙이고, 확인 칸은 프런트만 본다 — 1-E 전에는 비밀번호를 바꿀 길이 없어, 오타가 난 초기 비밀번호는 그 이메일을 묶어 버린다. 성공하면 「사용자를 만들었습니다」와 함께 상세로 간다.
- **사용자 상세**: 칸들, 상태에 따라 「비활성화」(destructive) 또는 「활성화」 하나(`user.update`). 가진 역할마다 「빼기」(destructive), 줄 수 있는 역할 고르기 + 「부여」(`role.assign`). 성공하면 `["admin", "user", id]`·`["admin", "users"]` 를 무효화한다.
- **역할**: 역할마다 권한 목록과 「효력 없음 — 빼세요」 표시. `can['role.manage']` 면 superuser 역할 밖의 역할에 권한 고르기 + 「부여」, 부여마다 「빼기」(destructive).
- **작업 로그 이름표**: 8절 표의 아홉을 더한다.

R6 줄을 빼면 이 시험이 실패한다.
  - **마지막 관리자**: ① 함수 직접 — 트랜잭션 안에서 「대상이 유일한 활성 보유자」면 거절, 비활성 보유자의 회수·이미 비활성인 대상은 통과. ② **동시 요청** — 활성 관리자 A·B 둘. 시험 연결이 **각 요청이 쓸 행**을 먼저 `FOR UPDATE` 로 잡아 둔다 — 비활성화는 대상의 `users` 행, 역할 빼기는 대상의 그 `user_roles` 행이다. 「A 가 B 를 비활성화」·「B 가 A 를 비활성화」를 함께 보내고, `pg_locks` 에서 앱 연결 둘이 기다리는 것을 본 뒤 푼다(잠금이 있으면 먼저 온 쪽은 행을, 다른 쪽은 `roles` 행을 기다린다). 정확히 하나 204, 하나 409·`last_admin` 행이고 활성 관리자가 1명 남는다. 교차 판(「A 가 B 를 비활성화」·「B 가 A 의 admin 역할을 빼기」, 잡는 행은 B 의 `users` 행과 A 의 `user_roles` 행)도 같다. **`FOR UPDATE` 줄을 빼고 돌려 두 시험이 실패하는 것을 확인한다**(D15 5.2) — 잠금이 없으면 둘 다 셈 2 를 본 뒤 시험이 잡은 행을 기다렸다가 둘 다 성공한다.

  - A-403: 운영자 200·편집자 403. `member` 에 넣어 둔 관리 권한이 `effective: false` 다. 질의 수가 역할·부여 수와 무관하다.

## 15. 검토 초점 — 시험이 다루지 않지만 사람이 쓸 때 문제가 될 것

1. **만든 계정의 비밀번호**: 관리자가 정한 초기 비밀번호를 사용자에게 전하는 길은 시스템 밖이다. 1-E 전에는 사용자가 바꿀 수도, 관리자가 재설정할 수도 없다. 샌 비밀번호를 막는 수단은 비활성화뿐이다.
2. **로그인 직후 15분**: 로그인이 창을 열어서(Q2), 막 로그인한 탈취 세션은 비밀번호를 다시 묻지 않고 계정·역할을 바꾼다. 원문이 받아들인 위험이다(D18).
3. **요청 중 비활성화된 요청자**: B 의 요청이 인증을 지난 뒤 A 가 B 를 비활성화해도, B 의 그 요청은 끝까지 간다. 활성 관리자 ≥ 1 은 지켜지지만 「방금 막은 사람의 마지막 한 번」은 남는다.
4. **역할 권한 부여의 파급**: `operator` 에 권한 하나를 주면 그 역할의 모든 보유자가 다음 요청부터 갖는다. 역할 화면은 보유자 수를 보이지 않는다.
5. **마지막 관리자가 비밀번호를 잊으면**: 자기 계정 금지·마지막 관리자 잠금이 잠김을 막지만, 비밀번호 재설정(1-E)이 없어 복구는 DB 직접 수정뿐이다.

- **Q18 → (a)**: 입구는 A-402 상세 하나, 비활성 대상도 받는다. 이메일 입구는 계정 존재를 묻는 길과 판정 갈래를 늘린다. 틀렸을 때 비용은 POST 하나와 폼 하나.

아래는 결정 전에 적은 선택지다.

### Q18. A-405 의 대상 — 비활성 계정과 이메일 입구

- 원문: 대상은 본문의 `user_id` **또는** `email`이고, 이메일은 「정규화해 **활성 회원**을 찾고 없으면 404」다(D19 A-405 입력표). 같은 표의 거부 조건은 「대상이 비활성 계정 — **거부하지 않는다.** 역할과 활성 상태는 별개다」다. 원문 코드는 이메일이면 활성 회원만 찾고, `user_id` 면 활성 여부를 보지 않는다.
- 엮인 것: 원문의 이메일 입구는 A-403 화면의 폼이다(UUID 가 화면에 보이지 않아서). A-402 상세는 `user.update` 가 있어야 열린다. 그래서 상세에만 입구를 두면 `role.assign` 은 있고 `user.update` 는 없는 역할은 부여할 화면이 없다(지금 씨앗에는 그런 역할이 없지만 A-404 로 만들 수 있다). 원문의 「부여 현황 조회 GET `role.assign`」도 같은 자리다.

| 선택지 | 근거 | 비용 |
|---|---|---|
| (a) 입구는 A-402 상세 하나(`user_id` 경로). 비활성 대상도 받는다 | 거부 조건 문장 그대로. API·화면이 가장 적다. 7절의 두 API 그대로 | 이메일 입구가 없다. `role.assign` 만 가진 역할은 쓸 화면이 없다 — 그런 역할을 만들면 상세 GET 권한을 다시 봐야 한다 |
| (b) (a) + A-403 에 이메일 입구(`POST /api/admin/users/roles {email, role_id}`, 부여만). 이메일은 활성 회원만 찾고, `user_id` 는 비활성도 받는다 | 원문 문서·코드와 같은 모양. `role.assign` 만으로 부여할 수 있다 | API 하나, 화면 폼 하나, 시험이 는다. 같은 계정이 입구에 따라 404 이기도 하고 아니기도 하다 |
| (c) (b) 와 같되 이메일도 비활성 계정을 찾는다 | 「역할과 활성 상태는 별개」를 두 입구에 똑같이 | D19 입력표의 「활성 회원」과 다르다. 이메일로 비활성 계정의 존재를 확인할 수 있다(`role.assign` 보유자에게만) |

답이 정해지면 6절 A-405 의 두 문단, 7절 표, 8절(이메일 입구 행), 12절 시험을 채운다.

### Q19. R6 이 활성화에도 걸리는가

- 원문 문서: R6 은 「superuser 보유자에 대한 계정 조작(**비활성화·삭제·타인 비밀번호 재설정 강제**)은 superuser 만」이다(D15 5.1, D19 A-402 거부 조건도 비활성·삭제). 같은 D19 의 재인증 행은 「**활성화도 같다** — 막아 둔 계정을 여는 것이다」라고 쓴다.
- 원문 코드: 네 동작(비활성·활성·삭제·재설정) 모두에 R6 을 건다(`guardAccountOp` 주석 「reactivation opens an account someone locked」).
- 닿는 결정: Q11 이 탈취 대응을 비활성화로 정했다. 활성화에 R6 이 없으면, `user.update` 를 받은 비-superuser 가 superuser 가 막아 둔 관리자 계정을 다시 연다.

| 선택지 | 근거 | 비용 |
|---|---|---|
| (a) 활성화에도 R6 을 건다 | 원문 코드, D19 재인증 행의 논리. 막은 사람(superuser)만 다시 연다 | D15·D19 의 R6 목록 문장과 다르다 — ondolith-j 결정으로 적는다 |
| (b) 활성화에는 걸지 않는다 | D15·D19 의 R6 목록 그대로. 늘리는 방향이라 마지막 관리자 잠금도 필요 없다(Q10) | 비-superuser 가 비활성 관리자 계정을 연다. 그 계정의 비밀번호를 아는 사람이 다시 superuser 가 된다 |

답이 정해지면 4절 R6 문장, 7절 활성 행의 403 목록, 12절 비활성·활성 시험을 채운다.
