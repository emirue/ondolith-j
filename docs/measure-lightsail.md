# Spring Boot 백엔드의 Lightsail 메모리 실측

**질문**: Spring Boot 백엔드와 PostgreSQL 을 Lightsail 512MB 또는 1GB 인스턴스 한 대에 함께 올리면 도는가, 메모리를 얼마나 쓰는가.

프런트(React)는 S3 + CloudFront 로 따로 배포할 계획이라 범위 밖이다(`src/front` 는 비워 둠). 실제 Lightsail 인스턴스가 아니라 **맥의 Docker 에서 `--cpus`·`--memory` 로 티어를 흉내 내어** 쟀다.

## 결론

- **512MB: 올릴 수 있다.** 판단 기준인 S6·S7(앱 상한 180m)이 **3회 모두 통과**했다. 180m 은 실제 Lightsail 512MB(`nano_3_0`)에서 PostgreSQL 과 앱을 올린 뒤 남은 약 180MB 에 맞춘 근사값이다.
  - **여유는 없다.** 앱은 유휴 때 이미 178–180 MiB 를 썼고, cgroup 최고도 180.1–180.3 MiB 로 상한에 붙어 있었다. 남는 몫이 180MB 보다 작으면 이 결과는 보장되지 않는다.
- **1GB: 돈다.** S5 가 3회 모두 통과했다.
  - 실제 1GB 서버에서 PostgreSQL 을 올린 뒤 남는 메모리는 실측한 적이 없다. 그래서 말할 수 있는 여유는 S5 의 cgroup 최고(320.4–327.8 MiB)와 상한 512m 의 차이, **약 184–192 MiB** 까지다.
- **ondolith(Go) 와 크기 비교**: ondolith 앱은 유휴 **4 MiB** 였다. Spring Boot 는 상한을 가장 넉넉히 준 512m 에서 유휴 **251.2–261.6 MiB**(상한의 절반쯤)를 썼다. 128m·180m·256m 에서는 유휴 때 이미 상한 근처(127.6–252.4 MiB)까지 썼다.
  - 이것은 기능이 같은 비교가 아니라 **런타임 바닥 크기의 비교**다. ondolith 는 쇼핑몰 화면을 그린 뒤, 이 앱은 API 두 개다.
  - 「Java 가 N MiB 를 필요로 한다」가 아니라 「그 상한을 주었을 때 N MiB 를 썼다」로 읽는다.
  - DB 유휴는 46 MiB(`shared_buffers=128MB`)로 ondolith 의 33 MiB 보다 컸다. 넣은 데이터와 질의가 달라서 같은 조건의 비교는 아니다.
- **참고(S1~S4)**: ondolith 와 같은 배분(앱 128m)은 JVM 기본값(S1)으로는 **3회 모두 실패**했고, J2 옵션(S2)으로는 **3회 모두 통과**했다.

| ID | 티어 | DB `--memory` | `shared_buffers` | 앱 `--memory` | JVM 옵션 |
|---|---|---|---|---|---|
| S1 | 512MB | 384m | 128MB | 128m | J1 |
| S2 | 512MB | 384m | 128MB | 128m | J2 |

- **J1** = 옵션 없음(JVM 기본값). **J2** = `-Xss512k -XX:TieredStopAtLevel=1`: 힙은 그대로 두고 스레드 스택을 줄이고 C2 컴파일러를 끈다.
- S6·S7 은 DB 와 앱 상한의 합(564m)이 티어를 넘는다. DB 상한은 ondolith 와 같은 조건을 맞추려는 것이고, 앱 상한이 실제 서버의 남는 몫을 흉내 낸다.
- S3·S4 의 통과는 「앱이 256MB 를 쓸 수 있으면 돈다」까지만 뜻한다. 실제 512MB 서버에서는 PostgreSQL 과 같이 있으면 그만큼 남지 않는다.

## 읽는 법과 한계

- **판정**은 회차마다 다음을 모두 만족해야 통과다.
  1. 유휴 측정 때와 부하 뒤에 모두 `Running=true`, `OOMKilled=false`
  2. 앱 로그의 `OutOfMemoryError` 0건
  3. `ab` 두 번 모두 완료 5000건, `Failed requests` 0, `Non-2xx` 0. 요약 줄이 없으면(`ab` 가 끊김) 실패다
- ondolith NFR-101 의 「앱 유휴 ≤ 티어의 절반」과 「앱 + DB ≤ 티어」는 **판정에 쓰지 않았다.** `docker stats` 값은 `--memory` 상한을 넘을 수 없어서, 이 배분에서는 두 조건이 늘 참이 된다. 값은 표에 적기만 했다.
- **메모리 지표**: 「유휴」와 「부하 중 최고(표본)」는 `docker stats` 의 MemUsage 다(ondolith 의 측정 스크립트와 같은 지표).
  - 「부하 중 최고(표본)」는 `ab` 가 도는 동안 1~2초마다 뜬 표본의 최댓값이다. 회차당 표본이 1~18개라 진짜 최고를 놓칠 수 있다.
  - 「앱 cgroup 최고」는 커널이 기록한 `memory.peak` 이다. 정확한 최고치이며 기동 때와 파일 캐시까지 포함한다.
  - 128m 에서 128.1 MiB 처럼 상한을 조금 넘는 값이 나왔다. 원인은 확인하지 않았다.
- **처리량**은 노트북 Docker 에서 잰 값이라 회차 사이 편차가 크다(S6 목록 191.70–247.75). 배분별 통과·실패를 판단하는 보조 값으로만 본다.
  - J2(C2 끔)인 S4 가 J1 인 S3 보다 처리량이 높게 나왔다. 원인은 확인하지 않았다.
- **`OutOfMemoryError` 검사는 실제로 잡아내는지 확인하지 못했다.** 21회 모두 0건이었다. 컨테이너는 살아 있는데 Java 힙이 모자라 500 을 내는 실패가 한 번도 나지 않았기 때문이다. 세는 명령 자체는 돌았다.
- **아키텍처**: arm64 에서 쟀다. Lightsail 인스턴스와 아키텍처가 다르면 숫자가 조금 다를 수 있다.
- **범위 밖, 하지 않음**: 실제 Lightsail 인스턴스 측정(비용), React·S3 배포, GraalVM native image.
- DB 계정 `m`/`m` 은 포트를 열지 않는 일회용 측정 컨테이너용이다.

## 다시 재기

```bash
# 1. 빌드 (테스트는 DB 가 있어야 돌므로 bootJar 만)
docker volume create bench-gradle
docker run --rm --cpus=2 -v "$PWD/src/back":/src -w /src -v bench-gradle:/root/.gradle \
  eclipse-temurin:25-jdk ./gradlew --no-daemon -q bootJar

# 2. 측정 (한 번에 하나씩. 스스로 nice 19 로 다시 실행된다)
./measure.sh env          # 아키텍처·java -version → results/env.txt
./measure.sh S6 1         # 시나리오 S6 의 1회차. 판정 실패면 exit 1, 하네스 실패면 exit 2

# 3. 표 만들기, 정리
scripts/summarize.sh      # results/ → 마크다운 표
./measure.sh clean        # bench-* 컨테이너·네트워크·gradle 볼륨 삭제
```
