# 요청서: ondolith 코어를 Spring Boot + React 로 다시 만드는 일

사용자가 ondolith 세션에 요청해 보낸 것입니다. 측정을 마친 뒤 사용자가 시작하라고 하면 진행하세요.

작성: 2026-11-11, ondolith 세션 (사용자 요청)
원본: ondolith 저장소 `~/projects/emirue/ondolith` (GitHub `emirue/ondolith`, 공개, Apache-2.0). **읽기만 한다.** 아래 Dxx 는 그 저장소 `docs/` 의 문서 번호다.
이 글은 public 저장소에 커밋될 수 있어서 실제 메일·홈 절대 경로·비밀 값을 넣지 않았다. 저장할 때 `scripts/check-public.sh` 를 돌린다.

0. 받는 순서 — 바꾸지 않는다
━━━━━━━━━━━━━━━━━━━━
1. 진행 중인 측정(S3~S7)을 끝낸다. 결과와 결론을 커밋한다. 이 요청 때문에 측정을 끊지 않는다.
2. 새 feature 브랜치를 만든다.
   - 측정 앱(`src/back`), `measure.sh`, `results/` 는 지우거나 덮지 않는다.
   - 코어는 측정 앱과 다른 경로에 둔다. 경로는 6단계 스펙에서 정한다.
3. CLAUDE.md 갱신안을 사용자에게 보여 주고 승인받는다.
   - 지금 CLAUDE.md 는 측정 전용이라 새 방향과 부딪힌다: 「질문 하나에 답한다」 범위, 「새 의존성을 추가하지 않는다」, 「`src/back` 은 요청서대로 고정」.
   - 그대로 이어 가는 것: public 저장소 규칙, 한국어, TDD, advisor, 작업 방식, CPU·메모리 절약.
4. 이 요청서를 저장소(`docs/` 권장)에 저장한다. `scripts/check-public.sh` 를 통과시키고 커밋한다.
5. 2절의 결정 항목을 사용자에게 묻는다. 답을 받기 전에는 그 영역을 구현하지 않는다.
6. 설계 문서(스펙)를 쓰고 사용자 승인 → 구현 계획 → Phase 0 부터 차례로.
   - 이것은 새 시스템이라 설계부터 한다: `superpowers:brainstorming` → `superpowers:writing-plans`.
   - 구현은 `superpowers:test-driven-development`. 한 번에 다 만들지 않는다.

━━━━━━━━━━━━━━━━━━━━
1. 무엇을 만드는가
━━━━━━━━━━━━━━━━━━━━
- ondolith 의 기능을 백엔드 Spring Boot(API)와 프런트 React(SPA)로 다시 만든 **코어**다.
- 코어는 공개 저장소다. 실제 사이트는 별도의 비공개 저장소가 코어 릴리즈를 받아 쓴다. ondolith 와 ondolith_community 의 관계와 같다.
- **배포형 제품이다** (D00 제약 3). 설치처마다 DB·PG·도메인이 다르다. 우리 환경을 가정한 하드코딩은 금지다.
- 대상 사용자 (D00): 개발자가 아닌 사이트 운영자, 제작 대행사, 테마 개발자.

사용자가 정한 것:
| 항목 | 내용 |
|---|---|
| 백엔드 | Spring Boot 4.1.2 / Java 25 / Gradle Kotlin. 측정 조건과 같다. 착수할 때 최신 판을 공식 문서로 다시 확인한다 |
| DB | PostgreSQL (ondolith 와 같은 18) |
| 프런트 | React + Zustand + TanStack Query(React Query) + Tailwind CSS |
| 배포 | 프런트는 S3 + CloudFront, 백엔드는 Lightsail |
| 저장소 | public |

━━━━━━━━━━━━━━━━━━━━
2. 구현 전에 사용자에게 물어야 하는 결정 (먼저 풀어야 함)
━━━━━━━━━━━━━━━━━━━━
D00 은 세 가지 제약을 두고 「깨면 그 제안은 틀렸다」고 적는다: 런타임 테마 교체, 단일 바이너리·저사양, 배포형 제품. React SPA 를 S3 에 따로 두는 구조는 앞의 둘과 직접 부딪힌다. 아래는 그래서 생기는 결정이다. 각 결정의 선택지와 영향을 정리해 사용자에게 묻고, 답을 스펙에 적은 뒤에 그 영역을 만든다.

**D-1 테마** (FR-301~313, A-202·A-203·A-212, D17·D40·D41)
- 지금: 테마는 html/template 파일 묶음이고, 비개발자가 재컴파일·재시작 없이 바꾼다.
  - zip 업로드가 된다. 디스크 테마가 내장 테마를 덮어쓴다.
  - 테마가 `admin.json` 으로 관리자 화면을 선언한다.
  - 템플릿이 실패하면 반쪽 페이지 대신 500 과 내장 오류 화면이 나간다.
  - 부팅 때 `requires` 버전을 검사한다.
- SPA 에서는 빌드된 JS 묶음이 화면을 그린다. 그래서 「파일을 바꾸면 다음 요청부터 적용」이 그대로는 안 된다.
- 선택지 (ondolith 세션은 고르지 않았다):
  - (가) **런타임 토큰·레이아웃 설정.** 테마 = 색·글꼴·간격 토큰 + 코어가 미리 만든 레이아웃 변형 선택 + `admin.json` 같은 선언. API 가 내려주고 SPA 가 런타임에 적용한다. 재빌드가 없는 대신 테마 자유도가 코어가 준비한 범위로 줄어든다.
  - (나) **테마별로 따로 빌드한 프런트 묶음을 런타임에 바꿔 끼운다.** 자유도는 크다. 하지만 「Go 를 몰라도 테마를 만든다」던 약속이 「React 를 알아야 한다」로 바뀌고, 테마마다 빌드가 필요하다.
  - (다) **공개 화면은 서버(Spring)가 템플릿으로 그리고 관리자 화면만 SPA.** ondolith 테마 모델을 가장 많이 살리고 D-2 도 함께 푼다. 대신 프런트가 두 갈래가 되고, 공개 화면은 S3 에 올라가지 않는다.
- 묻기 전에, 각 안에서 FR-301~313 이 각각 살아남는지·바뀌는지·없어지는지 표로 만든다.

**D-2 검색 노출·링크 미리보기** (FR-510·511·718·719, P-901·902)
- 지금: 서버가 그린 HTML 에 메타·OG·트위터 카드·JSON-LD·canonical 이 들어 있다. `sitemap.xml`·`robots.txt` 도 서버가 낸다.
- SPA 는 처음 받는 HTML 이 거의 비어 있다. 메신저 링크 미리보기(카카오톡 등)와 일부 검색 로봇은 JS 를 실행하지 않을 수 있다. 그러면 글·상품을 공유했을 때 미리보기에 사이트 공통 정보만 나올 수 있다.
- **이건 추정이다.** 각 서비스의 공식 문서로 확인한 뒤 사용자에게 가져간다.
- 선택지:
  - 공개 화면을 빌드 때 미리 렌더한다;
  - CloudFront 앞단에서 로봇 요청에만 메타를 넣는다;
  - 공개 화면을 서버에서 렌더한다 (D-1 (다)).
- `sitemap.xml`·`robots.txt` 는 어느 경우든 API 가 동적으로 낸다.

**D-3 배포 단위와 NFR 재정의** (NFR-102·103·106·301·304·305·306, FR-101~110)
- 지금의 약속:
  - 업그레이드 = 바이너리 교체 + 재시작;
  - 바이너리와 PostgreSQL 외에 설치할 것이 없다;
  - 크론·큐는 프로세스 안에서 돈다;
  - 리버스 프록시 없이도 동작한다;
  - 터미널 없이 브라우저에서 설치가 끝난다.
- 바뀌는 것: 배포 단위가 jar(+ JRE)와 프런트 묶음 둘이 된다.
  - 프런트는 S3 에 올리고 CloudFront 캐시를 무효화해야 해서 「서버 파일 하나 교체」가 아니다.
  - 설치 마법사도 프런트가 이미 S3 에 있어야 시작된다.
- 할 일: 각 NFR 을 버리지 말고, 새 구조에 맞게 다시 쓴 문장을 사용자에게 승인받는다. 예: 업그레이드 절차 단계 수의 상한, 릴리즈 산출물 목록, 설치 마법사가 동작하는 조건.

**D-4 Lightsail 티어** (NFR-101)
- 측정 결론을 근거로 512MB 와 1GB 중 목표 티어를 사용자와 정한다.
- 측정 앱은 API 두 개짜리라, 코어 전체는 더 클 수 있다. 기능을 붙일 때마다 같은 방법으로 다시 잰다.

3. 기능 전체 — 영역별
━━━━━━━━━━━━━━━━━━━━
기능별 상세(완료 기준·화면 입출력·정책값)는 **ondolith 원문이 단일 출처**다. 여기서는 영역마다 무엇을 하는지, 새 구조에서도 반드시 살아남아야 하는 규칙, 원문 위치만 적는다. 빠짐이 없는지는 부록 표로 확인한다 (8절).

**3.1 설치** (FR-101~110, P-001·002, D20 부팅, D71)
- 미설치 상태면 모든 요청이 설치로 간다. 폼 한 번으로 끝난다: DB 접속, 관리자 계정, 사이트 이름, 사이트 유형.
- 마이그레이션은 자동으로 돈다. 설정 파일 권한은 0600 이다. 재시작 없이 운영 모드로 전환된다.
- 실패하면 원인을 화면에 그대로 보인다. 내부 오류를 드러내도 되는 곳은 설치 화면뿐이다 (NFR-210).
- 이미 쓰고 있는 DB 를 덮어쓰지 않는다.
- **설정 파일이 깨지면 설치 모드로 돌아가지 않고 기동을 멈춘다** (FR-110). 지나가는 사람이 사이트를 다시 점유하는 것을 막는다.
- 설치 트리와 운영 트리는 서로 다른 라우트 트리다. 미설치 상태에서는 설치 API 만 존재한다. 프런트의 분기는 편의일 뿐이고, 강제는 API 가 한다.
- D71 의 「방화벽으로 막고 설치」 권고를 유지한다. 설치 요청도 CSRF 대상이다 (NFR-205).

**3.2 인증·세션·권한** (FR-201~218, P-101~113, A-401~406, D15, D74, D60 세션·비밀번호)
- 기능:
  - 이메일 + 비밀번호 로그인;
  - 서버측 세션 (쿠키에는 식별자만), 로그인 때 세션 ID 재발급, 로그아웃 때 파기;
  - 회원가입과 가입 닫기 설정;
  - 이메일 인증: 기본 켬. 인증 전 계정은 글쓰기·주문 불가. 링크는 1회용이고 만료가 있다;
  - 비밀번호 재설정;
  - 소셜 로그인과 계정 연결·해제. 마지막 로그인 수단은 해제할 수 없다;
  - 내 정보: 역할·권한 필드는 받지 않는다;
  - 탈퇴: 비활성화가 기본이고, 주문 이력이 있으면 삭제하지 않는다;
  - 프로필 항목 정의: 개수 제한이 없다. 정의는 행, 값은 JSONB;
  - 스팸 방지: honeypot 칸, Cloudflare Turnstile 은 선택;
  - 아이디 저장 쿠키;
  - rate limit.
- 계정 열거 방지:
  - 로그인 실패 사유를 구분해 알리지 않는다;
  - 가입·재설정 응답이 계정이 있는지 드러내지 않는다;
  - 관리자의 공개 표시 이름에 로그인 이메일을 쓰지 않는다 (NFR-212).
- RBAC (D15 1~2절): 역할–권한–사용자 구조, 내장 역할 5개, 권한 38개, 게시판별 권한, 기본 매트릭스.
- 검사는 서버에서 세 겹으로 한다 (D15 4절). 메뉴를 숨기는 것은 보안이 아니다 (D15 4.3).
- 권한 상승 방어 (D15 5절):
  - 권한 사다리 차단;
  - 마지막 관리자 보호: 동시 요청 두 건 중 하나만 성공한다;
  - 계정 삭제 대신 비활성화;
  - 파괴적 작업에는 재인증;
  - 역할이 바뀌면 세션 처리.

**3.3 테마** (FR-301~313, A-202·203·212, D17·D40·D41)
- D-1 결정 전에는 구현하지 않는다.
- 어느 안을 고르든 지켜야 할 의도:
  - 비개발자가 재빌드 없이 사이트 모양을 바꾼다;
  - 테마에 비즈니스 로직을 넣을 수 없다. 테마는 준비된 데이터만 받는다 (FR-305);
  - 테마가 깨져도 반쪽 페이지 대신 일관된 오류가 나간다 (FR-312);
  - 코어보다 높은 버전을 요구하는 테마는 내장 테마로 대체한다 (FR-313);
  - 업로드를 유지한다면 압축 해제 경로를 검증한다 (Zip Slip);
  - 테마 자산으로 테마 폴더 밖 파일에 접근할 수 없다;
  - 로고·파비콘;
  - 테마가 선언하는 관리자 화면과 그 값.

**3.4 페이지·메뉴** (FR-401~405, A-301~303·A-204·A-310, P-202)
- 슬러그 주소. 중복은 거부한다.
- 초안·발행 상태. 초안은 비로그인에게 404 다.
- 페이지별 템플릿 지정 (D-1 영향). 메뉴 트리.

**3.5 게시판** (FR-501~515, A-304~309, P-203~214, D30, D60 리치 텍스트·파일 업로드)
- 관리자에서 게시판을 만들고 설정한다: 권한, 첨부, 댓글, 스킨, 갤러리 목록.
- **커스텀 필드 스키마**(이름·타입·필수·선택지)를 정의하면 코드 수정 없이 폼과 목록에 나타난다. SPA 에서는 API 가 스키마를 내리고 프런트가 동적 폼을 그린다.
- 글 쓰기·수정·삭제와 조회수, 대댓글, 첨부.
- 검색은 PostgreSQL 전문검색. 페이지네이션은 큰 오프셋에서도 무너지지 않아야 한다. 정렬·필터의 정렬 키는 허용목록으로 검사한다. 비밀글.
- 리치 텍스트:
  - 허용목록으로 정화한 HTML 만 저장한다. 검색·요약은 그 HTML 의 평문을 쓴다;
  - **한글 IME 조합 입력(ㅎ→하→한)이 브라우저 시험에서 그대로 남아야 한다.**
- 사진: 긴 변 1920px 로 줄이고 480px 썸네일을 만든다. EXIF 회전을 반영하고 EXIF 는 지운다. 픽셀 수 상한을 넘으면 디코드하기 전에 거부한다.
- 지도 블록 (FR-716): 본문에는 스크립트 없이 지도사·좌표·확대·이름만 남는다.
- 게시판마다 테이블을 만들지 않는다 (DEC-3.9). 목록 조회에 N+1 이 없어야 한다 (NFR-105).

**3.6 커머스** (FR-601~627, P-301~514, A-501~517, D50·D30·D14·D73)
- 사이트 유형이 「일반」이면 커머스 라우트가 **존재하지 않는다** (FR-710). 숨기는 것이 아니다. API 에 없어야 하고, 프런트는 메뉴를 감춘다.
- 기능 목록:
  - 상품, 옵션 조합별 재고·품절, 카테고리, 상품 검색;
  - 장바구니. 비회원은 세션 기반;
  - 주문 상태머신. 전이는 코드로 강제한다;
  - PG 어댑터 인터페이스는 PG 중립, 구현은 토스페이먼츠. 승인 때 쓰는 시크릿 키의 Basic 인증은 서버에서만 한다;
  - 10분 만료 복구;
  - 웹훅: 서명·출처 검증, 재전송에도 멱등;
  - 배송비 정책, 배송·송장;
  - 반품·교환: 교환할 조합의 재고를 요청 시점에 예약한다. 같은 상품의 다른 조합으로만 교환한다. 차액은 추가 결제하거나 환불한다;
  - 약관 버전과 동의 기록;
  - 영수증: 주문 시점 스냅샷만으로 재발행한다;
  - QR 라벨 (값은 variant id), 입고·실사·피킹 (스캔, 바코드는 유일).
- 금액 규칙 — 반드시 그대로 옮긴다:
  - **금액 위변조 검증**: 요청 금액과 콜백 amount 가 다르면 승인하지 않는다;
  - **승인 멱등성**: DB 부분 유니크 제약으로 강제한다;
  - 취소·부분환불: 누적 환불이 결제 금액을 넘지 않는다. 품목 단위로 하며 **금액은 서버가 스냅샷에서 계산하고 요청 금액을 받지 않는다**;
  - 주문 할인은 품목에 배분하고, 배분 합계가 할인액과 정확히 같아야 한다;
  - 금액 표현은 D30 「금액」.
- 카드 정보는 저장하지 않는다 (DEC-3.7).

**3.7 관리자** (FR-701~719, A-101~604, D13·D19)
- 관리자 셸: 권한 없는 메뉴는 그리지 않는다. 진짜 보안은 서버 검사다.
- 대시보드.
- 사이트 설정: 사업자 정보를 푸터에 표시하고, 쇼핑몰 모드에서 표시 의무 항목이 빠지면 경고한다.
- 사용자·역할, 게시판 설정, 상품·주문.
  - 목록의 모든 페이지와 각 행의 상세에 링크로 닿아야 한다. 주소를 직접 쳐야 하면 FR-706 을 못 지킨 것이다.
- 작업 로그.
- 메일: SMTP 설정과 시험 발송.
- 소셜 로그인 설정, 사이트 유형 설정.
- 기간 조회: 하루의 경계는 서버 시간대다 (D19 0.6).
- 백업 내려받기·자동 백업: 최고 관리자가 비밀번호를 다시 확인해야 하고, 작업 로그에 남는다.
- GA4, 지도 키, 파일 저장소(로컬 / S3 호환), 검색 노출 설정, 구조화 데이터.
- 관리자 화면은 직접 구현한다 (DEC-3.10). 화면마다의 입력·검증 규칙은 D19 에 있다.

**3.8 운영** (D70·D71·D72)
- 헬스체크, 시스템 정보, 웹훅 수신 이력, 백업·복원 절차.
- 시간대: 서울 리전 Lightsail 도 기본은 UTC 라, 설치할 때 맞춘다.

4. 보안 — 가장 먼저, 가장 엄격하게
━━━━━━━━━━━━━━━━━━━━
**4.1 public 저장소 위생**
- 공격자가 코드를 전부 읽는다고 가정한다. 숨겨서 지키는 것은 없다. 방어는 코드와 설정에 있어야 한다.
- 커밋 금지: 지금 CLAUDE.md 목록 + `.env`·실제 설정 파일·DB 덤프·업로드·백업. `.gitignore` 로 막고 `*.example` 만 커밋한다.
- 테스트·시드에는 누가 봐도 가짜인 값만 쓴다.
- **프런트 빌드 변수(`VITE_*` 등 번들에 들어가는 값)는 전부 공개다.** 비밀을 넣지 않는다. 프로덕션 소스맵을 올릴지는 정해서 적는다.
- CI:
  - `pull_request` 트리거만 쓴다. `pull_request_target` 금지;
  - 워크플로 권한은 read 로 최소화한다;
  - 서드파티 Action 은 커밋 SHA 로 고정한다;
  - 비밀은 GitHub Secrets 에만 둔다.
- GitHub 설정은 **설정 변경이라 사용자 승인 후에만** 한다. 먼저 현재 상태를 확인해 보고한다: secret scanning, push protection, Dependabot alerts, private vulnerability reporting, `main` 보호.
- `SECURITY.md` 에 취약점 제보 경로를 둔다. 연락 수단은 사용자에게 묻는다.
- 의존성: 추가하기 전에 취약점(OSV 등)과 유지 상태를 확인한다 (ondolith NFR-209, `.ai/MISTAKES.md` M1). 잠금 파일을 커밋한다.

**4.2 ondolith 에서 그대로 옮길 앱 보안** (상세: D60·D15, 체크리스트 D86)
- 인증·세션·CSRF·업로드 검증을 직접 만들지 않는다. Spring Security 와 검증된 라이브러리를 쓴다.
- SQL 은 파라미터 바인딩만. 정렬 컬럼처럼 바인딩할 수 없는 값은 허용목록으로 검사한다.
- 비밀번호는 bcrypt 이상.
- 세션 쿠키: HttpOnly·SameSite=Lax·(TLS 면) Secure. 세 플래그를 단언하는 테스트가 있어야 한다.
- CSRF 는 상태를 바꾸는 모든 요청에 적용한다. 설치도 포함이다.
- 응답 헤더: 프레임 금지·nosniff·Referrer 축소·CSP. API 응답과 프런트(CloudFront 응답 헤더 정책) 양쪽에 둔다.
- 오류 메시지가 내부 구조를 드러내지 않는다. 예외는 설치 화면뿐이다.
- 업로드 검증 네 겹 (첨부·사진 공통):
  1. 확장자·MIME·매직바이트 확인;
  2. 실행 권한 제거;
  3. 웹루트 밖에 저장;
  4. 파일명 재생성.
- 리치 텍스트는 서버가 허용목록으로 정화한 HTML 만 저장한다.
- **저장된 자격증명** (PG 시크릿, SMTP 비밀번호, Turnstile 비밀 키, 소셜 client_secret, S3 시크릿) — D60 「저장된 자격증명」:
  - DB 에 봉인해 둔다 (AES-256-GCM, 설정 키 이름을 AAD 로);
  - 봉인 키는 설정 파일(0600)에만 둔다;
  - 화면에 다시 보이지 않고, 작업 로그에 값을 남기지 않는다;
  - 무엇이 시크릿인지는 한 곳에서 판정한다.
- 화면 권한보다 큰 일을 할 수 있는 값(`site_url`, 폴더 경로, 프록시 헤더, secure 쿠키)은 설정 파일에 둔다. 기준은 D60 「설정값을 어디에 두는가」 한 절이다.
- SSRF: SMTP 호스트와 S3 엔드포인트가 169.254.0.0/16 으로 해석되면 접속하지 않는다.
  - **판정은 DNS 해석 뒤, connect 직전에 한다.** 저장 시점의 문자열 검사는 소용이 없다;
  - S3 엔드포인트는 호스트(·포트)만 받는다.
- 권한: 서버 검사, 마지막 관리자 보호, 사다리 차단, 파괴적 작업 재인증, 계정 열거 방지.
- rate limit: 로그인·관리자·공개 폼에 둔다. 프록시 뒤의 클라이언트 IP 는 신뢰하는 프록시가 준 값만 믿는다 (D20 `proxy_ip_header`).
- 로그인 뒤 돌아갈 주소 `next` 는 내부 경로만 받는다 (D86 1.8).
- 백업 내려받기는 최고 관리자 + 비밀번호 재확인 + 작업 로그.

**4.3 프런트·백엔드를 나눠서 새로 생기는 위험**
- **같은 출처로 둔다.** CloudFront 하나에 프런트(S3)와 `/api/*`(Lightsail)를 붙인다. 그러면 CORS 가 필요 없고 쿠키 세션도 그대로 쓴다. 다른 출처로 두면 CORS 허용목록과 쿠키 SameSite 를 다시 설계해야 한다.
- **`/api/*` 는 CloudFront 에서 캐시하지 않는다.** 캐시되면 한 사람의 로그인 응답이 다른 사람에게 나간다. 쿠키와 필요한 헤더를 원본으로 넘긴다. 정책 이름과 설정은 AWS 공식 문서로 확인한다.
- **원본 우회를 막는다.** CloudFront 를 거치지 않고 Lightsail API 에 바로 닿으면 CloudFront 의 보호를 비켜 간다. 인스턴스 방화벽, CloudFront 만 아는 헤더 확인 같은 방법을 AWS 문서로 확인해 쓴다. 클라이언트 IP 는 CloudFront 를 거쳐 온 연결일 때만 그 값을 믿는다.
- **SPA 의 CSRF**: 쿠키 세션과 SPA 를 함께 쓸 때 Spring Security 가 공식 문서로 안내하는 방식을 쓴다. 직접 만들지 않는다.
- **인증 정보를 localStorage·sessionStorage 에 두지 않는다.** 세션은 HttpOnly 쿠키로만 다룬다. Zustand persist 에 사용자·권한을 저장해 권한 판단 근거로 쓰지 않는다.
- **비밀이 든 주소** (D60 「비밀이 든 주소」):
  - 재설정·인증 링크의 토큰은 SPA 가 받자마자 API 에 POST 로 넘기고, `history.replaceState` 로 주소창에서 지운다;
  - 그 경로에서는 GA 같은 외부 스크립트를 싣지 않는다;
  - 소셜 로그인 콜백은 API 가 받아 리다이렉트로 끝낸다.
- **XSS**:
  - React 의 기본 이스케이프를 믿는다;
  - `dangerouslySetInnerHTML` 은 서버가 허용목록으로 정화한 본문에만 쓰고, 쓸 때마다 사유 주석을 단다 (ondolith NFR-203 의 `template.HTML` 규칙과 같다);
  - 주소를 `href` 에 넣을 때는 스킴 허용목록(http·https·mailto·tel)으로 검사한다.
- **업로드 파일은 프런트 버킷과 다른 비공개 저장소에 둔다.** 언제나 API 가 권한을 검사한 뒤 내려준다 (D60 「파일 저장소」: 공개 주소·서명 주소를 화면에 싣지 않는다).
- 프런트의 라우트 가드는 편의다. 모든 권한 판단은 API 가 한다.

5. 프런트엔드 — React (체계적으로, 멋지게)
━━━━━━━━━━━━━━━━━━━━
**스택**
- 사용자 지정: React, Zustand, TanStack Query, Tailwind CSS.
- 권장 (확인 후 채택): TypeScript(strict), Vite, 라우터(React Router 등), 폼(React Hook Form + Zod 등), 테스트(Vitest + Testing Library, E2E 는 Playwright).
  - react.dev 는 프레임워크 없이 시작하는 경로로 Vite 를 안내한다.
  - **판과 API 는 기억으로 쓰지 않고 공식 문서나 context7 로 확인한다** (ondolith 규칙 7).
- 백엔드 계약: API 를 OpenAPI 로 기술하고 프런트 타입은 거기서 생성한다. 손으로 맞추지 않는다.

**구조 규칙**
- 상태 경계:
  - 서버에서 온 데이터는 TanStack Query 에만 둔다;
  - Zustand 는 클라이언트 UI 상태(사이드바, 장바구니 서랍, 미리보기 등)에만 쓴다;
  - 서버 데이터를 Zustand 에 복사하지 않는다.
- 폴더는 기능(도메인) 단위로 나눈다 (install, auth, account, pages, boards, shop, cart, orders, admin/…). 공용은 shared(ui·lib·api) 에 둔다.
- 화면 컴포넌트는 직접 fetch 하지 않는다. 기능별 query·mutation 훅을 거친다. 쿼리 키는 기능마다 한 곳에서 정의한다.
- 공개 사이트와 관리자를 코드 분할한다. 방문자가 관리자 코드를 받지 않게 한다.
- API 오류는 한 곳에서 다룬다: 401 은 로그인으로, 403 은 권한 없음 화면으로, 422 는 폼 필드 오류로. 서버 검증이 기준이고 클라이언트 검증은 편의다.
- 게시판 커스텀 필드와 회원 프로필 항목은 서버가 내려준 스키마로 동적 폼을 그린다 (FR-503·FR-215).
- 사이트 유형이 일반이면 커머스 화면과 메뉴가 없다 (FR-710).
- 리치 텍스트 에디터는 **한글 IME 조합 입력을 브라우저 시험으로 먼저 확인한 뒤** 고른다 (FR-513).
- 휴대폰 폭부터 만든다. 키보드 조작·포커스·대비를 지킨다. ondolith 는 전 화면을 세 가지 폭으로 쟀다.
- 문자열은 한 곳에 모은다 (NFR-403, 다국어는 구조만).

**쓸 스킬** (이 맥에 설치돼 있다)
- `frontend-patterns`: React 구조, 상태 관리, 성능 패턴
- `frontend-design:frontend-design`: 시각 방향과 타이포그래피. 템플릿 같은 기본 디자인을 피한다
- `antislop`, `antislop-ui`: 색·레이아웃·컴포넌트
- `antislop-human`: 대비·키보드·포커스·상태 (접근성)
- `antislop-layoutmobile`: 휴대폰부터 데스크톱까지의 레이아웃
- `example-skills:webapp-testing`: Playwright 로 실제 브라우저 시험

6. 백엔드 — Spring Boot
━━━━━━━━━━━━━━━━━━━━
- 패키지는 도메인 단위로 나눈다: install, auth, account, rbac, content(pages·menus·settings), board, media, commerce(catalog·cart·order·payment·shipping·returns·inventory), admin, ops(backup·health·logs). 순환 의존 금지.
- API: JSON REST. 오류는 일관된 형식(Problem Details, Spring 지원 여부 확인)으로 낸다. OpenAPI 문서를 생성한다.
- 마이그레이션: 부팅 때 자동 적용한다. 되돌리는 길을 문서로 남긴다 (NFR-302·303·308). 도구는 공식 문서로 확인해 고른다.
- DB: PostgreSQL.
  - JSONB(커스텀 필드·프로필 값), 전문검색, 부분 유니크 제약(멱등)을 쓴다;
  - 금액 규칙은 D30 을 따른다;
  - 스키마 출발점은 ondolith D30 이다.
  - ondolith 테이블 41개: attachments board_fields boards cart_items carts categories comments email_verification_tokens media menus operation_logs order_agreements order_items orders pages password_reset_tokens payments permissions posts product_categories product_images product_options product_variants products refund_items refunds return_items returns role_permissions roles sessions settings shipments social_accounts terms theme_items theme_settings user_fields user_roles users webhook_events
- 백그라운드 작업(자동 백업, 가상계좌 입금 기한 만료 등)은 같은 프로세스 안의 스케줄러로 돌린다. 별도 워커·크론을 두지 않는다 (NFR-103 의 의도).
- 외부 API 주소(토스 등)는 코드에 둔다. 사이트마다 다른 값은 설정에 둔다 (D60).
- 토스 연동 사양은 D50 「검증된 연동 사양」과 D73 에 있다.

**부록 A**: D10 표에서 FR·NFR 행을 기계적으로 뽑는다.
- 열: ID · 요구사항 · 우선 · Phase · 처리 · 메모.

- 대조 개수 (ondolith 세션이 오늘 셈): **FR 114 + NFR 37 = 151행.** FR-206 처럼 폐기된 행도 포함이다.

  - FR-301~313 → D-1;
  - FR-510·511·718·719 → D-2;
  - NFR-101 → D-4;
  - NFR-102·103·106·301·304·305·306 → D-3;

  - NFR-402·NFR-404·NFR-405·NFR-407 → Go 도구를 Java·React 게이트로 옮김.

**부록 B**: D11 에서 P-·A- 화면을 뽑는다.
- 열: ID · 화면 · 처리 · 메모.
- 대조 개수: **공개(P) 67 + 관리자(A) 50 = 117.**
- 메모 칸 미리 채울 것:
  - P-9xx (sitemap·robots·오류·웹훅·테마 자산·헬스체크) → SPA 화면이 아니라 서버 엔드포인트;
